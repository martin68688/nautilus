① 蒸馏原料：一条完整的演化路径

来源：run 20260516_104127_spooky-author-identification（后期已修复数据泄露的 run，无 <0.1 的泄露节点）

故事：从欠拟合基线（log loss 1.09）一路优化到 0.32，中途因换小模型 + 超时退化到 0.61，再用注意力池化部分恢复。

step10 · draft · log loss=1.0902
初始基线：MultiResolutionAuthorClassifier + DeBERTa-v3-large + 63 个手工特征。严重欠拟合（acc~40%，接近随机）。
step16 · improve · log loss=0.3872 ↓0.703 ★大幅改善
关键转折：删掉手工特征 + 用标准 AutoModelForSequenceClassification。plan："hand-crafted features drown out the transformer signal"
step22 · debug · log loss=0.3196 ↓0.068 继续优化

step46 · debug · log loss=0.6129 ↑0.293 ★退化

为什么这条路径是蒸馏的金矿：它同时包含成功转折（step16 删手工特征，↓0.703）、持续优化（step22 修 bug，↓0.068）、失误退化（step46 换小模型，↑0.293）、和部分恢复（step49 注意力池化）。原版 Trace2Skill 会合并成 1 个 skill 文件，丢失了转折点和冲突。

② 蒸馏产物：8 个结构化 skill

下面是从这条路径蒸馏出的 skill。绿色=降低 log loss 的有效 skill，红色=升高 log loss 的失败 skill，黄色=条件/警告。metric_delta 中 绿色↓=变好（log loss 下降），红色↑=变差。

S1 · 小数据 transformer 微调：删手工特征，用标准 AutoModel
SOP-NATIVE-001 · distilled from step16
SOP当 transformer 在小文本分类任务上欠拟合时，删除所有手工特征（文体/统计/n-gram），改用标准 AutoModelForSequenceClassification 直接喂原始文本。
条件transformer backbone val log loss > 0.8（欠拟合） 手工特征 > 50 维
证据Δ log loss: ↓0.703 step 10→16 run 20260516_104127
plan 原文"the hand-crafted features drown out the transformer signal... a standard AutoModelForSequenceClassification achieves much better"
失效模式文体学任务（作者归因）可能仍需少量手工特征（见 S4 的条件分支）
S2 · mean pooling + multi-sample dropout 防过拟合
SOP-POOL-002 · distilled from step22
SOP用 mean pooling（over non-padding tokens）替代 CLS token + multi-sample dropout（K 次前向平均）提升泛化。
条件DeBERTa val log loss 已达 0.3-0.5 平台
证据Δ log loss: ↓0.068 step 16→22
依赖需先修 head_mask bug（DebertaV2Model.forward 不再接受 head_mask）
S3 · 为避免超时换 deberta-v3-small（退化）
FAIL-SMALL-003 · distilled from step46
失败模式为避免 6h 超时，从 deberta-v3-large 换成 -small + 减 epoch。log loss 从 0.32 反升到 0.61。省时的代价是性能大幅退化。
条件6h 超时限制 原用 large 模型
证据Δ log loss: ↑0.293 step 22→46
plan 原文"training is too slow and gets killed by the timeout... use a smaller, faster model (deberta-v3-small)" —— 这个权衡判断在 spooky 上是错的，small 模型容量不足。
S4 · multi-head attention pooling 补救小模型（部分有效）
SOP-ATTN-004 · distilled from step49
SOP在 deberta-v3-small 上加 multi-head attention pooling（可学习注意力权重聚合 token）部分弥补容量损失。
条件已换成 small 模型 欠拟合（log loss > 0.5）
证据Δ log loss: ↓0.185 step 46→49 但仍未回到 step22 的 0.32
警告部分恢复，非最优。证明"换小模型"是错误决策，attention pooling 只是缓解。应回退到 large + 优化超时方案。
C1 · 条件：6h 超时限制
COND-TIMEOUT-005
类型Condition 节点
关联triggers → S3（换小模型失败） applies_when → S4（attention pooling 补救）
价值这个条件是 S3（失败）和 S4（部分恢复）的共同前提——超时压力下，换小模型是错的，attention pooling 是缓解。这正是工程约束导致决策分叉的真实案例。
★ S2 ↔ S3 冲突边（prevents）
CONFLICT-001 · auto-detected

冲突类型：双真冲突（同任务、相反模型选择策略）

S2：用 large + mean pooling + dropout → log loss 0.32（本路径最优）

S3：换 small 模型省时 → log loss 0.61（退化）

判定依据：同任务（spooky）+ 相反模型规模选择 + metric 客观判定 S2 胜（0.32 < 0.61）。→ prevents 边，S3 对跖于 S2。教训：在 spooky 这类需要容量的小数据任务上，不应为省时换小模型。

S5 · refines 链：原生微调 → mean pooling → attention pooling
RELATION-001 · auto-detected
关系S1（原生 AutoModel）→ refines → S2（+mean pooling）→ refines → S4（+attention pooling）
证据链1.09 → 0.39 → 0.32（S1→S2 持续降 log loss）
分支S4 是在 S3（换小模型）之后的补救，所以 S4 refines S2 但带了"小模型"条件——这是条件化 refines，不是简单线性细化。

④ 这次蒸馏揭示的关键洞察

洞察 1：工程约束（超时）是冲突的根源（C1 的价值）

S2（large 模型，log loss 0.32）和 S3（small 模型，0.61）共享超时约束 C1。原版合并成一句"注意超时"，丢失了"换小模型是错的"反面知识。改进版用 prevents 边保留对立——agent 检索到 S3 时，自动看到对跖的 S2 警告。

洞察 2：失败的 plan 原文是金矿

S3 的 plan 写着"use a smaller, faster model (deberta-v3-small)"——看似合理但在 spooky 上是错的（容量不足）。原版不会提取这个错误推理，改进版作为 failure_mode 保留。

洞察 3：refines 边有 metric 证据

S1→S2 是有 log loss 证据的 refines 链（1.09→0.39→0.32，持续下降）。不是 LLM 主观判断。这正是你"metric_delta 验证 patch"的核心价值。

洞察 4：这些 skill 直接可入双曲图

每个 skill 都有：① SOP（→角度θ）；② Δ log loss（→半径r，越低越好→r越小）；③ 条件（→applies_when）；④ 失败模式（→prevents端点）。这才是双曲 skill 图的真实节点数据。
